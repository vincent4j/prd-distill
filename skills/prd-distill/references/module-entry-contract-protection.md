# 开发前模块入场与合同保护

当用户要求开发已有模块的新功能、修复模块 bug、调整模块行为，或提到当前会话不熟悉的模块概念时，先把 PRD Distill 当作模块入场检查使用。

## 定位模块

1. 如果存在 `docs/prd/README.md`，先用用户提到的模块名、术语、接口、页面、数据字段、受影响文件或 `git diff` 关键词检索模块索引。
2. 只读取命中的索引行和相邻上下文，用来定位模块、主 PRD 和合同文件。
3. 如果多个模块同样可能，先问用户确认；不要在没确认的情况下猜模块边界。

## 索引与按需读取

1. 不要默认全文加载大型 PRD、合同、worklog 或 memory 文件。
2. 根据模块索引命中结果找到主 PRD 和合同文件路径。
3. 使用关键词、受影响文件名、接口名、字段名、页面名、合同 ID 或近义词，先在目标 PRD / 合同中检索相关章节。
4. 如果存在 `docs/memory-keeper.md`，只在 bug、回归、用户说“以前遇到过”、高风险模块或 PRD 命中不足时，用当前模块名、错误现象、字段名、接口名、文件名、模型名和合同 ID 等关键词检索相关条目。命中的内容只作为历史经验和合同候选，生效约束仍以 `docs/prd/contracts/` 为准。
5. plans / worklogs / memory 只能作为补充输入：在 PRD / 合同命中不足、需要追溯根因、需要判断合同候选成熟度或用户明确要求时读取。
6. 只读取命中的章节、相邻上下文和相关合同条目。
7. 只有命中不明确、改动跨模块、触碰核心流程 / 数据字段 / 安全边界、或合同冲突时，才扩大读取范围。
8. 如果用户提到陌生概念，先在模块索引、模块 PRD 和合同中搜索该词和近义词；只有文档里找不到时才问用户解释。

## 保护既有合同

1. 改代码前列出本次可能受影响的生效合同或关键 PRD 规则。
2. 不要做会破坏生效合同的实现改动。
3. 如果新需求与既有 PRD / 合同冲突，停止实现，明确列出冲突点、受影响的 PRD / 合同条目、继续修改可能造成的后果，并请求用户确认是否变更规则。
4. 只有用户明确确认后，才能同步更新 PRD / 合同并继续实现。

## 开发自测覆盖合同

1. 实现完成进入自测时，再回到相关 PRD / 合同中确认本次实际触碰了哪些约束；不要等到提交前才第一次做合同覆盖判断。
2. 自测范围按“本次功能实际影响”收窄：只覆盖被本次代码或行为改动触碰的合同条目，不按当天所有 diff 或模块里所有合同扩大测试。
3. 合同条目绑定了测试命令的，在自测阶段运行对应测试；合同条目要求运行证据的，在自测阶段检查或补充日志、截图、接口响应等证明。
4. 如果某个受影响合同暂时无法验证，必须明确说明原因、风险和后续需要补的测试。
5. 如果合同没有测试绑定，但本次改动触碰了合同覆盖的行为，要补测试或在收尾中明确记录测试缺口。
6. 自测证据必须可追溯，但不强依赖 worklog：最终回复至少说明受影响合同、验证方式和结果；如有日志、截图、接口响应或大文件证据，先落盘到 `/tmp/<project>-*` 并给出路径。只有项目已有且本轮正在使用 worklog / plans / memory 时，才同步写入这些记录；不要为了本 skill 强行创建 worklog。

## 收尾证明

最终回复说明：

- 读取了哪些模块 PRD 章节 / 合同条目。
- 哪些合同被本次改动影响。
- 自测阶段跑了哪些测试，或复用了哪些运行证据。
- 还有哪些风险未闭环。
